## Corrección de arranque: el aislamiento NO es una base por usuario

Tomás planteó "que cada usuario tenga su DB propia, como Mati en Arc One". El **objetivo**
(baúles que jamás se mezclen, escala, seguridad) es correcto, pero el **mecanismo** no:
- **No es una base por usuario.** Es **una sola base con aislamiento por fila**: cada fila lleva
  `user_id` y **toda consulta filtra por el usuario logueado del lado del backend (Cloud Run),
  nunca confiando en el cliente.**
- Es lo que **ya estaba canonizado** (Documento Madre §5, "dos mundos de datos") y lo que hizo
  Mati en Arc One (aislamiento por `user_id`/workspace a nivel fila). Se eligió así porque
  **escala a +100k** y permite compartir el contenido global de M0. Una-DB-por-usuario no escala.
- Tres capas de seguridad, ahora explícitas en M4 §5: **Firebase Auth** (identidad) +
  **`WHERE user_id` en el backend** + **Cloud Storage carpeta por usuario**.

## M4 — Baúl (lógica ✅ v1)

- **Casi sólo lectura:** lee `entregas` ⨝ `fotos` ⨝ `cartas` (global). Su única escritura es el
  **borrado**. No captura nada (eso es M3).
- **Dos modos de orden (toggle)** — *decisión Tomás*: **Reciente** (default, lo último arriba) y
  **Más valoradas** (4-5 ⭐ arriba; sin valorar = NULL → al final). **No** es orden compuesto: como
  hay una carta/día, "fecha → estrella" no reordena nada; el compuesto queda para v2 (2 rituales/día).
- **Borrado real, para siempre** — *decisión Tomás*: botón discreto 🗑 → **modal claro + botón
  rojo** que dice exactamente qué se pierde ("la carta, tu reflexión y tus fotos… no se puede
  deshacer"). **Sin papelera** (el modal es la red de seguridad). El borrado limpia **fila
  `entregas` + filas `fotos` + archivos en Cloud Storage + el link compartido si existía**.
- **Sin métricas de vanidad** (rachas/contadores). Las entradas a medias (`completada=false`) se
  muestran sin reproche.
- **Editar** una entrada → diferido v2. En v1 una entrada cerrada es fija.

## M5 — Compartir (lógica ✅ v1)

- **El desafío real (lo identificó Tomás):** "hay muchos pasos hasta que el receptor llega a la
  carta". **Reframe canónico:** el link es un **regalo completo, no un embudo.** Recibir = abrir
  la URL = listo (web abierta, sin instalar, sin login). Instalar es sólo para quien quiere el
  suyo a diario. Los "pasos" sólo existen si obligamos a instalar para recibir — no lo hacemos.
- **Engagement del receptor (v1):** (1) nota personal del que comparte arriba (es de una persona,
  no una marca) · (2) carta interactiva y bella, mismo gesto de girar · (3) un solo CTA suave
  abajo ("una carta así, cada día, para vos") → onboarding. **El motor de engagement es la
  calidad de la carta (M0)**; compartir sólo la expone.
- **Dos modos:** **carta sola** (frase+prompt+dibujo, sin datos tuyos, invitación) y **ejercicio
  completo** (carta + reflexión + fotos, íntimo).
- **Privacidad:** compartir el ejercicio completo vuelve reflexión+fotos **públicas-por-link** →
  **aviso explícito antes de generar** ("cualquiera con el link va a poder verlas"). La carta sola
  no lo necesita. Link **unlisted/no indexable** pero público para quien lo tenga (se dice claro).
- **El link muere con la entrada** — *decisión Tomás*: borrar en M4 el ejercicio compartido
  **apaga el link** (`activo=false` → "ya no está disponible"). Tus datos íntimos no sobreviven a
  que los borres. La **carta sola** (sin datos privados) puede sobrevivir como invitación.
- **Técnico:** URL `/c/{token}` con **token aleatorio opaco** (jamás `entrega_id`/`user_id`/IDs
  secuenciales). Página **server-side** desde la web (Expo for Web / dominio propio), mobile-first,
  sin login/cookies. Fotos vía URL pública/firmada de Cloud Storage atada al token.
- **Tabla nueva `compartidos`** (privada, `user_id`): `token · entrega_id · carta_id · modo
  ('carta_sola'|'ejercicio_completo') · nota · activo · creado`.

## Refinamiento M5 (mismo día, post-cierre): experiencia del receptor

Tomás afinó cómo recibe el que abre el link. Canonizado en M5 §2:
- **La página del link ES el destino, no un trampolín.** El receptor ve el regalo completo, lo
  **gira y lo lee SIN login** (el flip es parte de *ver*, no de "interactuar" → va libre).
- **CTA suave al final, opcional** — lo puede ignorar y cerrar. **No se lo empuja al onboarding.**
- **El login NO es peaje para ver:** aparece sólo si toca el CTA (tener baúl propio pide
  `user_id`). Frontera: ver/leer = libre · crear algo mío (completar carta / tener las propias) =
  pide cuenta.
- **CTA honesto:** *"Configurá tu cuenta para tener tus propias cartas"* (no "completá esta carta";
  la recibida puede no estar en sus categorías). v2: la recibida = carta de prueba del onboarding.
